Linear correction

The analytic reference builds Stage 1 as an XYZ matrix, equivalent to a working-RGB matrix by change of basis. Its nine control degrees of freedom have three distinct roles: one for exposure, two for source-white adaptation and six for color relationships around a fixed destination white.

Separate the nine degrees of freedom

Global Exposure supplies one degree of freedom: a common gain that changes luminance without changing chromaticity. Source White supplies two more, placing the neutral at the chosen destination white.

The remaining six controls shape color relationships around that fixed white. Both Balance controls change colored-pixel luminance. Both Spread and both Heading controls also preserve luminance when Balance is zero.

These are independent control roles, not a claim that their matrices are orthogonal under a Euclidean matrix inner product. Exposure controls the global scale; adaptation places the neutral; directional correction shapes the colors around that neutral. The combined working-RGB matrix is

Many RGB mixers offer a preserve-luminance option. Preserving the white is a separate constraint: changing colored relationships should not move a neutral off the white you just established. Here every directional adjustment fixes that white by construction. This is the practical advantage of the six-control layout over editing nine unconstrained mixer coefficients.

Luminance and white preservation should not be conflated. The two Balance controls deliberately change the luminance of colored pixels while retaining white. Holding both an arbitrary white vector and every pixel’s fixed leaves four matrix degrees of freedom, not six.

Appearance coordinates and grading

Stage 1 is a linear color transform. The reference then repairs the input into its native AP1 cube and encodes it in modCAM16. Tone and Color operate on appearance coordinates; RGB export applies cube containment and decoding after Stage 3. This chapter introduces that representation, especially the coordinates used by the Color controls.

This part describes the current analytic model in libraries/perceptual-grade-reference. Archived 1.23.2 controls, instructions and measurements are identified separately. The frozen Blender implementation retains its earlier Warp ordering; Next Blender has not implemented Warp yet and will use the corrected reference. Product features and historical releases therefore need their own scope labels.

modCAM16 is a revised color appearance model in the CAM16 family. It describes how a color looks under specified viewing conditions, separating lightness, chromatic strength and hue. Perceptual Grade uses its revised relationships and Helmholtz–Kohlrausch compensation, which accounts for chroma’s contribution to perceived lightness.

Architecture and runtime

Historical implementation guidance: this chapter retains the 1.23.2 runtime, source layout, and validation profile. For current development commands and supported behavior, use the product READMEs in chromaticity.

The extension’s central job is to keep one current grade consistent while the reader edits controls, inspects scopes and renders through native nodes. The model owns the meaning of that grade. The runtime transports its values into the chosen evaluator and accepts completed work only when it still belongs to the current parameters.

An edit updates the grade's parameter state. Direct values can update immediately; a sampled color table becomes active only when its parameter signature still matches. Scopes evaluate cached input samples independently, and Color Reference remains diagnostic.

Follow a control edit

Grade and Stack pencils derive their highlight from the single diagram target in the current editor and its visibility. They do not store separate per-node activation flags. Clicking another pencil makes its node active and replaces the editor target; closing the diagram clears highlighting. A retained but inactive Stack target is reopened when its pencil is clicked.

A gesture or sidebar edit enters through ui and updates the selected Grade’s parameters (allocating a Grade only on the first actual edit). The model converts Linear controls into an exact matrix and Tone/Color controls into coefficients and curve data. Graph updates publish those values through the owning operator or timer. Changing the selected tonal region or UI page refreshes diagnostics without changing the grade.

The installed package root is src/blender. Its model modules implement matrices, appearance conversion, tone curves, color operators and sampling. The graph modules translate those results into native Shader and Compositor nodes. The ui modules own gestures and display; integration owns registration and cleanup. This separation lets a numerical change be checked before host evaluation enters the picture.

Keep evaluators on the same grade

The extension builds Direct and Baked LUT paths into stable native graphs. A template for each node-tree type is cloned for additional nodes, and node groups are saved with the Blender document. Ordinary edits update uniforms, curve textures and LUT images while preserving graph topology.

For ordinary forward nodes, Linear remains an exact matrix ahead of either nonlinear path. Direct evaluates the current Tone and Color parameters through native operations and curve tables. Baked LUT evaluates the analytic model on the fixed native ACEScg/ACES-white 0…1024 log1p grid, then supplies a paired native sampler. The evaluation chapter explains their numerical approximations.

A completed bake carries the signature of the parameters that produced it. The runtime publishes it only if that signature still matches the current grade, including during a drag. While forward work is pending, current Direct values provide the preview. Render preparation finishes pending work for the selected method. GPU draw callbacks advance numerical snapshots; they never publish images or construct graph links.

The DCTL is a separate analytic implementation of the same grade inside Resolve. Its sources live in src/dctl, and the build combines the analytic body with locale-specific control declarations. It does not use the Blender node graph or its bake scheduler; parity tests connect the implementations at the model boundary.

Cross compositor storage boundaries safely

Blender’s compositor can store intermediate images in float16 under Automatic precision even when shader arithmetic is float32. The graph must therefore account for where a temporary result becomes an image, rather than assuming every intermediate retains shader precision.

Cell addressing is fused into bounded UV coordinates and physical fractions. One texture stores the base RGB plane and three forward-edge planes, independently encoded with signed mantissas and power-of-two exponents. Four texture reads select one base and the three ordered edges; fused multiply-adds accumulate them. Encoding small differences before half-float transport avoids subtracting quantized neighboring vertices. Shader lookup retains raw vertices. Curve textures similarly store endpoint values and derivatives with power-of-two scaling.

Creative gain, H–K repair and decoding share a shader operation. Cone conversion, signed lift and opponent subtraction are also fused where separate half-float buffers would lose needed information. Alpha follows a separate outer path. Precision and CPU/GPU selection remain host settings; these arrangements make the extension’s graph respect their storage boundaries. The main implementation is in graph/compositor.py, graph/operations.py and graph/lut.py.

Image/RGB sources and supported grade chains can supply those samples directly. Render Layers resolves the scene, view layer and raw Combined pass through an owned 32-bit scene-linear EXR snapshot, sampling at most 256 by 192 pixel centers. A new render invalidates that cache. GPU context, scheduling and recovery

model/gpu.py owns the installed analytic float32 evaluator and nested-grid Baker; model/gpu_shader.py contains its runtime shader source. graph/gpu.py owns programs by window context, performs a float64-reference conformance probe, and registers draw handlers for Node, Viewport and Image editors. graph/lut.py uses these handlers for numerical dispatches and its timer for RNA/image publication. GPU objects never enter the CPU executor.

Background execution explicitly calls gpu.init() on the main thread without changing the render engine. Foreground execution requires a usable drawing surface. Losing that surface/window, shader errors and unavailable physical devices select the CPU. Matrix-only work and singular inverse matrices also remain on the CPU. The UI reports this choice without adding a render method.

Parameter textures have a stable capacity, are uploaded once per snapshot and are released on completion/cancellation. Input and output textures keep a fixed 1024×128 layout for tiny probes, partial batches and later edits; the output texture belongs to the cached program. This avoids repeated layout specialization. Adaptive batches target approximately 20 ms of warm numerical work; a cold shader/driver compilation is synchronous and can exceed this target. A batch includes input upload, the complete Grade sequence, readback, device audits, AP1 conversion and float32 storage. Flagged vertices share one CPU recovery pool at the end of each preview/refinement phase; a table cannot publish until that pool is repaired. The timer can publish a completed 33³ preview or 65³ final after a callback finishes. A stale final never replaces current controls.

Undo/load resets numerical jobs while retaining compiled programs. Full unregister removes draw handlers and releases those programs. Render/save completion reuses current finished cubes; pending foreground GPU work switches to CPU because lifecycle handlers have no guaranteed drawing context. If its matching preview has been published, CPU refinement retains every shared vertex. The float32 policy and audit are defined in the math specification.

Next Blender policy machines

This chapter documents the policy layer in products/perceptual-grade-next-blender. That product is a separate generation from the historical extension described by the other development chapters. The policies are deliberately host-free Python: they observe facts from Blender or a worker, reduce one event at a time, and return effects for a runtime consumer to perform. They do not call Blender, start threads, write images, or send process commands themselves.

Each machine is a small protocol:

state + event -> policy.step(...) -> new state + effects

An effect is the policy’s authorization for one external operation. The runtime executes it and feeds the resulting receipt back as the next event. This keeps the state transition testable while making the side-effect boundary explicit.

Grade settings remain authoritative. Runtime observations enter a pure reducer; only its effects authorize adapter operations, and receipts return as events. The parameter/image transactions are comparison examples, while compositor callbacks also use the production gate.

What a policy stores

The design goal is to store independent facts and derive readiness from them. The simplification candidates below identify places where the implementation still duplicates facts or phases. A signature is an immutable correlation key for a request. Job IDs, observer tokens, and render generations distinguish receipts whose lifetimes must not be confused. Absence is None; an empty string is never a stand-in for “no demand”.

The common safety rules are:

  • Correlation checks govern receipts. Stale helper generations and gesture tokens are ignored; a same-generation render identity mismatch fails the ticket. During a gesture, a superseded node result may still become a preview.
  • One-shot completion receipts cannot complete the same slot twice. Declarative node output effects deliberately repeat on idempotent events so the consumer can reconcile host state; preview receipts can also repeat.
  • A current failure clears the renderable installation and selects the visible error path. A stale failure cannot damage newer demand.
  • The consumer executes effects in order and reports success or failure. Policy code never performs a best-effort side effect in an exception handler.

The .inv files in requirements/ describe these transition contracts and examples. The verifier checks the declared properties against the Python source under their stated assumptions. It does not prove Blender’s native observations, image validity, thread affinity, worker implementation, or collection bookkeeping. The runtime tests and installed Blender tests cover those adapter premises.

Read an edge as event or receipt [condition] / requested effect; the condition and effect are omitted when unnecessary. Each box represents one phase, or one configuration of facts for a policy that has no phase field. Phase labels match the implementation; configuration labels describe derived states rather than additional stored flags. Sequential phases always have separate boxes. running and desired abbreviate preparation signatures; current and pending in the observer figure abbreviate tokens. The join’s pending count is derived from its three child flags, not stored as another counter. For synchronous transactions, success and failed abbreviate operation receipts. Entering a synchronous operation phase requests its namesake effect; those repeated effect names are omitted from edges. A semicolon separates alternative events. The helper’s operation effects are described in its lifecycle section.

A double border marks an absorbing state: later events cannot leave it. Some policies name that phase terminal; others retain names such as released or closed. Finality does not imply success. The publication transactions share their terminal phase between successful and failed paths, and resource retirement can finish without deleting anything. Ordinary states such as idle, node error, and helper failed can still transition and have a single border. The policy/effect-consumer overview above depicts data flow rather than states.

The figures emphasize lifecycle decisions; the prose describes correlation checks, unchanged-state receipts, and less common transitions. Explanatory notes and the numbered simplification candidates stay outside the boxes.

Preparation: latest demand, one worker

src/policy/preparation.py is used by src/runtime/preparation.py. Its state is just desired_signature and running_signature. A request always replaces the latest demand. If no work is running, the request also returns prepare_signature; otherwise it waits for the current physical worker to retire. A preview receipt publishes an intermediate result but does not free the running slot. A final receipt for the running signature retires that slot and, when a newer request exists, authorizes the newest successor.

A superseded success can still be delivered as a preview. A superseded failure is suppressed, and the latest demand is started after the old worker's final receipt.

The distinction between preview and final matters. The host preparation lane may produce a preview and then continue working. Treating the preview as retirement would allow a second job to overlap the physical slot. Conversely, withdrawing demand does not claim that the worker has stopped; its final receipt still provides the retirement fence.

The owning runtime also fences source lifetimes. request, collect, and wait in runtime/preparation.py do not let a caller’s cancellation release a slot before the executor function returns.

The three-child join

src/policy/preparation_join.py is the aggregate barrier used by src/runtime/grade_preparation.py. new(signature) marks linear, tone, and boundary pending. Each matching component receipt clears one bit. The final distinct receipt returns completion_signature; the first error is retained and returned only at that final point. Stale and duplicate receipts do nothing.

All three physical children retire before aggregate completion, including after an error. The runtime already wraps the receives in a shielded `asyncio.gather`; that is a scheduling fence in addition to this reducer's decision.

Each worker sends a component receipt to the join. `par` permits any completion order; the final distinct receipt authorizes assembly. Cancellation still waits for every physical worker through the shielded group.

The preparer launches all three functions before awaiting any one of them. It then assembles the PreparedGrade only after the join authorizes completion, checks that boundary geometry belongs to the same appearance context, and prepares the parameter atlas. This is why a first error cannot immediately release the executor slot.

Simplification candidate J1. The fixed three-child barrier could be expressed directly around asyncio.gather, reducing the explicit pending-bit reducer. That is safe only if the replacement still rejects stale or duplicate receipts, retains the first error until every child has retired, preserves cancellation shielding, and leaves proof evidence for those properties. The current reducer is verbose, but its contract is easy to audit independently of asyncio.

Node output policy

src/policy/node.py is the per-node decision layer. The runtime creates and updates it from nodes.py and consumes its effects in _consume_effects. The state records current demand, the installed signature and quality, whether a gesture is active, the preparation correlation signature, and an optional error. It does not store an output_mode flag. output_mode() derives one of current, preview, pending, or error.

Only this predicate permits rendering:

desired_signature == applied_signature
and desired_signature is not None
and applied_quality == "full"
and error is None

A new request may retain the last-good installation as a preview. A preparation receipt authorizes a build; an installation receipt records the resulting kernel. A current error removes the applied kernel from the policy state and selects the fail-closed output. A later request clears that error and starts again; recovery_result can also clear it when recovery installs a full result for the current non-None signature.

The preparation signature identifies shared prepared Grade data; the desired kernel signature can additionally identify the node’s graph context. A current preparation receipt must match both correlations. A superseded successful receipt is eligible only while a gesture is active, and becomes a preview rather than current output. Once current full output exists, later receipts cannot replace it; a preview cannot downgrade a full installation of the same signature. presentation reissues the derived output policy without starting new work. gesture_begin and gesture_release change only gesture participation; release does not discard a retained preview. request(None) clears demand and the applied kernel. dispose resets the entire lifecycle and emits only disposal, without a presentation effect. The consumer fences subscriptions and releases references through the resource policy.

The host shows a retained kernel as an updating preview. With no installed kernel, pending presentation may use an identity placeholder. A current error selects visible magenta output with alpha preserved; render preflight must not release a frame with this error or with merely pending/preview output.

Presentation is derived from authoritative demand and installation facts. A stale receipt cannot replace a current result, and a preview is never render-ready.

Preparation owns the worker slot, while the node owns presentation. A, B, and C name settings versions; preparation and kernel signatures still have their separate correlations. This trace runs outside a gesture, so an obsolete A cannot replace the retained Z preview. A preview receipt does not retire A. Current C is installed through the consumer, or its preparation failure selects visible magenta output with alpha preserved.

stack_replace and grade_changed are scalar observations. They may authorize reconciliation, but they do not themselves change the node’s kernel state. The runtime owns ordered Stack membership and Grade lookup; this proof does not prove those collections.

Simplification candidate J2. Rebuild observations return the same state and add a rebuild permission to the resulting presentation effect. A stateless policy helper could authorize that reconciliation while the lifecycle reducer continues to own presentation. This is a possible organizational reduction, not evidence of redundant stored state. Keep reconciliation behind an effect consumer, including on these state-preserving transitions.

Helper process lifecycle

src/policy/helper.py governs one helper process and one physical work slot. runtime/execution.py translates its effects into process and transport operations. The generation fences a process session; probe_id fences startup and active_id fences submitted work. The policy does not own payload queues or join implementation.

Startup proceeds from stopped to starting, then probing after hello, and to ready only after a matching successful probe. A preview publishes while the slot remains active. A final result or cancellation retires the slot before the next dispatch. An active cancellation sends a cancel request; it is not a receipt that the work has stopped.

Shutdown escalates from a channel shutdown request to terminate, kill, and an explicitly unretired condition. Physical exit settles work before cleanup is attempted.

The process and transport perform only operations requested by helper effects. Cancellation leaves active work owned until its final receipt or physical exit. Shutdown deadlines control escalation; cleanup begins only after exit and completes through its own receipt.

Failure or timeout moves a live process toward termination. A channel shutdown uses stopping; a process without that transport uses terminating. Terminate and kill timeouts lead to unretired, which keeps ownership visible rather than pretending cleanup succeeded. After physical exit, the policy publishes job and probe outcomes, queues cancellation or failure, and enters retiring. Cleanup may be retried; only a successful cleanup receipt reaches closed or failed. Cleanup failure itself requests no new work; a later shutdown event requests another cleanup attempt. failed can still become closed on shutdown, so only closed has the absorbing-state border.

Simplification candidate J3. A smaller lifecycle could remove generation or combine probe and active correlation only if the runtime contract guarantees process restart isolation and ordered receipts. Production bank publication

src/policy/bank_publication.py is the active production publication path. The parameter-image code in nodes.py constructs two packed image banks, while runtime/bank_publication.py consumes the reducer’s effects. The inactive bank is staged and checked before the selector changes. Selection is read back, then delivery publishes the resource and dispatches installation results to all affected node records.

An invalid active bank first closes output, then repairs both banks. A selection or delivery failure restores the old selector before failing closed.

The consumer writes the packed banks, reads back the selector, and dispatches installation receipts to Blender nodes. Alternative frames distinguish ordinary staging and repair. A failed selector change or delivery restores the old selector before bounded failure-output closure retries.

The admission facts require two distinct valid bank indices and an admitted publication context. If the active bank is invalid, repair_gate first waits for confirmed failure-output closure. Only then may repair_stage repair both banks. A failed stage or unclean pack fails closed. A wrong selector readback or delivery receipt enters restore_selector; the old bank and graph bindings are restored before the final failure output is attempted. The runtime bounds failed closure retries and reports indeterminate if it cannot establish a reliable output.

Both successful delivery and a successful closed receipt in fail reach the same terminal phase. The reducer does not store separate success and failure end states. A failed closure receipt remains in fail and requests another closure attempt; it has not reached terminal.

Simplification candidates B1 and B2. stage and repair_stage have the same receipt and outgoing transitions, so one phase could carry a repair effect variant while retaining the close-before-repair gate. The candidate bank is also mathematically 1 - active_bank for this fixed two-bank resource and is already derived by GradeResource; storing both indices duplicates a fact. Either change must retain the distinct-bank admission check, repair ordering, selector restoration, and fail-closed retry bound.

Publication strategies in the comparison example

The repository contains a publication comparison example under examples/publication_compare. Its policies are useful design experiments, but they are not one sequential production pipeline. Production uses the two-bank transaction above and the save-packing helpers described below.

Immutable parameter-image transaction

examples/publication_compare/policy/parameter_publication.py models a fresh immutable image: stage, snapshot, bind, commit, activate, deliver, then retire. Stage or snapshot failure goes directly to visible failure and retirement. Failure from binding through delivery enters the restoration sequence (restore_bindings, restore_metadata, restore_resource) first. The comparison node calls it from examples/publication_compare/nodes.py.

Its separate candidate_effect() permits reuse only when the candidate is not exposed, and allocation only while the pool contains fewer than three images. retirement_effect() protects current and candidate images; removal requires quiescence, zero native users, and no protection. These are allocation predicates, not extra phases of the binding transaction.

This strategy keeps the current and candidate versions separate through binding and activation. Every restoration component is attempted after a failed transaction.

This comparison-only sequence follows one fresh immutable candidate. Each operation returns a receipt before the next action is authorized. Failed binding through delivery enters restoration; every restoration component is attempted even if an earlier component fails.

Shared-image transaction

src/policy/image_publication.py is also exercised by the comparison example. It snapshots an existing image, uploads and packs when the snapshot is not already matching and clean, commits metadata, delivers, and retires. Upload, packing, or metadata-commit failure enters restoration. Restore-upload failure stops restoration immediately; restore-pack failure or an unclean restored image does the same. Only successful restoration of both reaches restore-metadata, after which the transaction still reports failure. Preparation or snapshot failure, and failed delivery, go directly to failure and retirement. Production save handling instead calls request_save_packing() and finish_save_packing() for a generated dirty parameter image. Those helpers do not claim a new publication.

The shared-image strategy can skip upload and packing when the captured image is already matching and clean. Its rollback still cannot make stale output current.

This comparison-only sequence changes one existing image. The clean-snapshot branch skips upload and packing. Restore-metadata is reached only after restore-upload and restore-pack succeed; failed restoration goes directly to visible failure and retirement.

Compositor supersession

src/policy/compositor_publication.py protects a compositor snapshot with a positive scene ID and epoch. It is used in production by PublicationGate for finished/reset evaluation callbacks and activity observations. Its live admit/superseded publication effect is used by the comparison example’s snapshot_commit() path. Admission of an eligible unprotected snapshot emits an epoch without changing state. The subsequent superseded receipt records the protected scene and epoch; a successful later completion for the same scene clears protection. Old epochs, other scenes, cancellation, and non-quiescent reset are ignored.

The production gate uses the callback and reset transitions; the live admission/supersession flow is comparison-only. Protection prevents a second live swap until a later evaluation completes.

Live admission and fresh-image binding belong to the comparison example. Production also delivers evaluation-finished and reset observations to the policy. An older epoch, a different scene, or an unsuccessful completion leaves protection in place.

Resource adoption and retirement

src/policy/resources.py contains two related decisions. may_adopt() is a predicate, not a state machine: owner, node, space, completeness, image validity, and image agreement must all be true. runtime/grade_resources.py uses it at the boundary where a persisted host resource is considered the installed resource.

The reducer sequences disposal and retirement. Disposal fences subscriptions, then detaches the node’s Grade and kernel references. Retirement observes the native resource. A live, owned, zero-user, unprotected resource is eligible for eviction; a non-live wrapper can be evicted directly. After eviction, the policy requires a fresh eligibility observation before native removal.

Adoption is a conjunction predicate. Deletion is a separate receipt sequence with a fresh zero-user and protection check.

Disposal optionally adds the fencing and detachment prefix to retirement. The consumer obtains native facts again after eviction, so the original zero-user observation cannot by itself authorize native deletion.

Simplification candidate R1. The disposal and retirement entry paths already share the suffix beginning at observe. Their two initial phases exist only to issue the first effect. An initializer returning (state, effects) could remove these entry phases, at the cost of a different runtime runner contract. This offers less benefit than B1/B2 or P1. Disposal must still fence and detach before observation; ordinary retirement must begin with observation. Native user counts remain authoritative; adding a Python ownership ledger would create a second, stale source of truth.

Gesture observer and participants

src/policy/gesture.py supplies scalar decisions to runtime/gesture_coordinator.py. The coordinator owns the per-window gesture collections, target filtering, and native event routing. The policy owns token allocation, observer handoff, phase checks, deferred completion, participant release, and undo permission.

Observer installation

The observer state has current_token and pending_token, plus a monotonically allocated serial. The first window observation invokes an installation. During a replacement, the current observer remains admitted while the new token is pending. Only an installation receipt for that pending token can promote it; failure leaves the current observer. A lost current observer may leave a pending replacement alive. Reset invalidates callbacks but preserves the serial. The figure separates pending installation with and without a current observer; losing the current observer while a replacement is pending moves between those configurations. Reset always clears both tokens, including from pending. Native input must match the current token; an explicit adapter event with token None remains allowed. Handoff also checks the captured gesture token and its armed/active phase. After installation, the coordinator replays the latest move/finish or requests handoff for a newer gesture.

A stale installation or loss receipt has no authority. The current observer stays usable until the pending native installation succeeds.

Gesture participation

The coordinator stores armed, active, and deferred finishing phases for each gesture, together with its participating node targets. Movement of at least three pixels on either axis crosses the active threshold. Release or cancel is deferred until the native widget has applied its final value; observation then authorizes participant completion. Activation begins a node gesture unless another active participant already owns it, in which case it requests a refresh. An armed gesture that finishes without activating refreshes a changed target. Only the final active participant releases a node. Native gestures do not authorize a manual undo checkpoint; manual undo is allowed only for an adapter-owned changed gesture.

The policy checks scalar token and phase facts. The runtime remains responsible for collection order, lookup, target filtering, and native event delivery.

Observer acknowledgement precedes token promotion. Movement activates participants; finishing waits until the native widget has applied its final value. The coordinator releases a node only when its final active participant finishes, with optional auto-keying and adapter-owned undo handled by its effects.

Render preflight

src/policy/render_preflight.py protects the render boundary. A ticket starts in waiting with a render identity, scene identity, frame, subframe, and generation. runtime/publication.py queues it and nodes.py performs the main-thread reconciliation before resolving it.

The ticket releases only when all correlation fields match, the event is a publication, the signature is non-None, it equals the published signature, and there is no error. A same-generation mismatch or failure enters failed. A stale generation is ignored so an old callback cannot fail a newer ticket. Terminal receipts do nothing. The non-None condition is precise: this reducer does not independently reject an empty string. Signature construction and other policy assumptions must establish any stronger signature format rule.

The gate queues and wakes the waiting thread, but the reducer authorizes release only for an exact published signature. A mismatch fails closed.

The render thread waits while Blender's main thread reads the exact frame and reconciles its Grade kernels. Admission can retry before reconciliation begins. An exact publication releases the ticket; a failure applies visible error output before delivering the failed ticket.

Simplification candidate P1. RenderPreflightTicket currently repeats the identity fields already held in its policy state so that cross-thread callers can construct plain events. A ticket could instead expose a correlation value derived from the state and centralize event construction. This is safe only if the state remains immutable to the waiting thread and every callback still passes the same render, scene, frame, subframe, and generation checks.

How the proofs should be read

The policy requirements are executable contracts, not a model of all Blender behavior. For example:

  • requirements/preparation.inv proves latest-demand replacement and receipt correlation; it does not prove executor cancellation.
  • requirements/preparation_join.inv proves the all-three barrier and delayed error; grade_preparation.py supplies the physical gather and shielding.
  • requirements/node.inv proves current/full/error presentation decisions; runtime checks and host tests must establish kernel structure, image contents, and graph ownership.
  • requirements/helper.inv proves generation and job fencing, escalation, exit ordering, and cleanup ownership; transport queue ordering remains an adapter contract.
  • The bank, image, and resource requirements prove fail-closed sequencing and eligibility predicates, while their consumers perform native operations and collect receipts.
  • requirements/gesture.inv proves scalar token, phase, participant, and undo decisions. It does not prove the coordinator’s collection bookkeeping.
  • requirements/render_preflight.inv proves exact release correlation and stale-generation handling. It does not prove that Blender’s scene snapshot is correct.

Some named requirements make the review points especially concrete. The preparation queue properties are running_request_only_replaces_latest_demand, final_receipt_starts_latest_successor, and obsolete_failure_does_not_publish_error. The join uses any_completion_order_joins_after_all_three and child_error_is_retained_until_last_retirement. The node uses full_quality_is_required_for_current_output, current_failure_clears_applied_output, and stale_full_result_updates_drag_preview. The helper uses stale_generation_is_ignored, cancel_request_retains_active_slot, and cleanup_failure_retains_owner_and_error. The production bank uses repair_requires_successful_closed_receipt, selector_change_requires_clean_staging_receipt, and failed_delivery_restores_original_selector. Resource deletion uses deletion_requires_eviction_and_fresh_eligibility; gesture behavior uses observer_handoff_commits_only_after_ack, last_participant_authorizes_release, and native_finish_never_pushes_undo; render release uses release_requires_correlated_exact_publication and stale_generation_cannot_release_or_fail_current_ticket. These are the concrete contracts behind the diagrams and the simplification notes above.

A simplification order

The strongest low-risk reductions are the ones that remove duplicated facts without weakening a correlation fence:

  1. Merge bank stage and repair_stage into one staging phase with an explicit repair effect, while preserving close-before-repair.
  2. Derive candidate_bank from the active bank for the fixed two-bank resource.
  3. Centralize render-ticket correlation construction so the ticket does not duplicate policy-owned identity fields.
  4. Consider replacing the fixed preparation join only after its physical retirement, first-error, duplicate-receipt, and cancellation guarantees have equivalent executable evidence.

Helper generations and gesture tokens are not redundant state: they protect against process restart and native observer replacement. Removing them would require a new runtime contract, not just a smaller diagram. Likewise, replacing the derived node presentation modes with stored booleans would make stale or partial output easier to present as current.

The inverse reference is the selected analytic/numerical inverse function; it is not an assumption that all grades have an exact round trip.

A deterministic screening subset uses 2,048 pixels per fixture. The four best balanced candidates, two best display candidates, two best absolute-RGB-p99 candidates, the baseline and explicit mandatory candidates enter full validation. Repeated choices count once. Every stored pixel is included in full validation; screening-excluded heldout distributions are also recorded. “Best” means best among that fully validated shortlist, rather than a proven optimum over every possible shaper or grade.

Metrics and ranking

For a reference RGB and sampled RGB , the per-pixel absolute scene error is

It is measured separately in Linear Rec.709, Linear Rec.2020 and ACEScg, using the stock OCIO conversions. Normalized error and relative error with a 0.001 denominator floor are also retained. Absolute RGB RMS is : it is the RMS of the per-pixel maximum-channel error, not an RMS pooled over channels.

The four output transforms are SDR 100 nits Rec.709/BT.1886, SDR 100 nits P3-D65/sRGB, HDR 1000 nits P3-D65/PQ and HDR 1000 nits Rec.2020/PQ, with D65 creative white and no additional look or view exposure. The P3 HDR path uses the same OCIO ACES 2.0 output built-in even though stock Blender does not list that display pairing in its UI. Rendered differences include absolute-light ΔE_ITP, luminance nits, encoded-channel error, display-linear RGB nits and fractions above ΔE_ITP 1, 2 and 5.

Each statistic is computed per fixture × exposure × workload, then the worst case is taken. Percentiles are not pooled across fixtures. The predeclared balanced objective minimizes the largest ratio to the previous grid across ten terms: four worst per-case rendered p99 ΔE_ITP values, three absolute scene-RGB p99 values and three absolute scene-RGB RMS values. All terms have equal standing in this minimax rule; a ratio above one identifies a regression. Ties use the worst rendered p99 and then the grid name. The rule requires a nonzero baseline error, so an identity-only grade is unsuitable for this ratio objective. Maxima and all other statistics remain in the tables even though they do not determine the ranking.

LUT sampling study: upper bound 128

This experiment compares LUT sampling coordinates while keeping the analytic grading function unchanged. It tests fixed Rec.2020/D65, native ACEScg/ACES white with a nonnegative axis, and AP1 primaries normalized to D65 with a signed axis. The experiment is separate from the current production sampling policy.

Eligibility and error

Let be the exact color entering the LUT, expressed in canonical Linear Rec.709/D65. For an ordinary forward Grade this is after Stage 1. For an inverse-roundtrip test it is the forward Grade result. For a Stack it is the input of the complete Stack, whose Stage 1 matrices are included in the bake.

Let convert canonical coordinates to Linear Rec.2020/D65, and convert them to standard ACEScg/ACES white using the stock Blender/OCIO conversion. The two eligibility masks are

[ m_R(\mathbf q)=\mathbf 1{T_R\mathbf q\in[0,10]^3},\qquad m_A(\mathbf q)=\mathbf 1{T_A\mathbf q\in[0,128]^3}. ]

They are independent masks, not their intersection. A pixel outside one domain does not contribute to that domain’s metric. A pixel outside both contributes to neither. Masks use strict float64 comparisons, are determined before candidate evaluation, and do not depend on the candidate’s gamut, shaper, bounds or approximate output.

Let be the full analytic reference and the result sampled with grid . The scene error, used only where , is

[ e_R^{(g)}(\mathbf q)= \left|T_R\left(\widehat F_g(\mathbf q)-F(\mathbf q)\right)\right|_\infty. ]

The infinity norm is the largest absolute error of the three RGB channels. It does not divide by brightness or reference RGB. The reported RMS is the RMS of these per-pixel maximum-channel errors.

For each ACES 2.0 output , let include rendering and the declared output encoding. For pixels with , the ranking uses

[ e_v^{(g)}(\mathbf q)= \left|V_v!\left(\widehat F_g(\mathbf q)\right)-V_v!\left(F(\mathbf q)\right)\right|_\infty. ]

The four outputs are SDR 100 nits Rec.709/BT.1886, SDR 100 nits P3-D65/sRGB, HDR 1000 nits P3-D65/PQ and HDR 1000 nits Rec.2020/PQ. ACES creative white is D65. There is no additional view exposure or look. Rendered RGB means encoded output RGB for the primary ranking. The tables also include absolute emitted RGB in nits, emitted RGB divided by output peak nits, luminance error and ΔE_ITP.

An empty domain has a null distribution. It is not treated as zero error. Eligible pixels outside a candidate’s grid are retained and extrapolated through the boundary tetrahedron; they are not discarded. coverage.csv records those counts separately from domain exclusions.

Three sampling bases

Standard ACEScg uses AP1 primary chromaticities and the ACES white . Its conversion includes stock Blender/OCIO Bradford adaptation to/from D65. This experiment’s AP1/D65 candidate keeps those AP1 primary chromaticities but recomputes their normalized primary matrix for D65 . AP1/D65 is an experimental sampling basis, not standard ACEScg.

For primary XYZ columns and normalized white XYZ , the normalized primary matrix is

[ N_{\mathbf w}=P,\operatorname{diag}!\left(P^{-1}\mathbf w\right). ]

The AP1/D65 coordinate conversion is . Adapting the entire native AP1 basis to D65 would instead reproduce essentially the same RGB sampling coordinates as native ACEScg with Bradford conversion, so it would not be a distinct gamut experiment.

Every candidate converts its lattice vertices back to canonical coordinates, evaluates the same , then stores the result in its sampling basis. Grade working whites remain D65, ACES and D50 in the three specified Grades, independently of the LUT basis. “No negative” describes the native AP1 lattice starting at zero; input and output RGB are not clipped.

With the upper bound fixed at 128, the native AP1 source cube reaches approximately −3.879…+131.879 in Rec.2020/D65 and −1.167…+129.167 in fixed-primary AP1/D65. The tested signed lower bounds are therefore −4/−8 and −2/−4 respectively. Native AP1 uses zero. The two D65 bases need extrapolation for some upper source-cube corners even with properly selected lower bounds. Full matrices and channel-wise extrema are in metadata.json.

Full forward and inverse math

This chapter contains the current reference specification alongside the retained Perceptual Grade 1.23.2 derivation. The current analytic authority is libraries/perceptual-grade-reference: section 6.5 describes its Stage 3, and section 20 its inverse and Stack oracle. Sections 6.3–6.4 and 9–19 retain the historical control set, signed-lift/fallback policy and deployed inverse machinery except where a current comparison is explicitly marked. Those historical profiles do not implement the corrected Warp ordering.

The equations assume fixed grade parameters and viewing conditions. An inverse need not have a slider representation. Equations describe real arithmetic; numerical branches and implementation profiles are stated separately. An algebraic reduction followed by scalar or two-variable root solving is called a semi-analytic inverse here. That term describes the retained production inverse, not the current reference search, and does not claim a universal closed form or global convergence.

For a fixed positive reference energy and positive requested lightness, the standalone H–K guard is one-to-one and has a unique inverse from a bounded, strictly monotone scalar equation. The retained production inverse nests that guard inverse inside a two-variable Stage-3 solve, then undoes Tone and Stage 1. The current reference instead evaluates the complete forward map for each candidate, with H–K repair before Scale and cube containment at RGB export; section 20 specifies that search.

The full grade can still have multiple preimages. Black clipping, singular matrices, signed extension, fallback selection, finite precision, and creative stage-3 folds require explicit policies. A fixed-reference guard inverse does not by itself establish injectivity of the complete grade.

20. The reference inverse

Sections 10–18 invert the 1.23.2 production stage: a two-unknown reconstruction with analytic hue elimination, a safeguarded scalar guard inverse, and a pooled damped Broyden refinement. The analytic reference takes a different approach. It has no per-component inversion of Stage 3 at all. It searches for preimages of the complete forward function and validates every candidate by running that forward function.

This section describes libraries/perceptual-grade-reference/src/inverse.py and the independent Stack oracle in src/stack.py. Read it instead of sections 10–18 when the question is about the reference; read those when the question is about the shipped DCTL or Blender inverse.

20.1 Contract

The entry point is solve(model, xyz, forward=None), returning InverseResult(value, residual, status) with three per-row arrays. value is XYZ in the model’s grading context; canonical grading RGB is the internal search and ranking coordinate. residual is the scaled maximum residual, and status is one of:

Each row starts from a set that is merged and de-duplicated:

  1. The linear prior — the least-squares solution through the Stage-1 matrix, which is exact when nothing nonlinear is active.
  2. The target itself and the zero vector.
  3. Scaled priors at times the prior, which bracket a wrong exposure.
  4. A offset stencil at , where the scale is . This is what recovers a preimage whose linear prior lands in the wrong basin.
  5. An analytic neutral preimage. The negative achromatic axis has a square-root chroma cusp that a smooth search can stall near, so the neutral case is solved directly: decode the target’s achromatic response, invert the tone curve for the magnitude, and reconstruct the neutral RGB. It is still passed through the same forward validation as every other seed, so it is a better starting point, not a trusted answer.

The relative scaling is what makes the tolerance meaningful for both very dark and very bright targets; an absolute tolerance would be unreachable in one and trivial in the other.

Ranking differs by outcome, and the distinction matters:

  • When any root exists, roots rank by distance to the prior, so the nearest-linear root wins and the result stays close to the least-squares preview.
  • When no root exists, candidates rank by residual first and prior distance second, so the reported approximation is the best reproduction available rather than the nearest one.

Lexicographic RGB breaks remaining ties. This matters because several seeds can converge to the same root with bitwise-different coordinates; without the tie-break the selected value would depend on seed order and batch composition, and the same input could return slightly different output in different batch shapes.

20.6 No nested guard inverse

Every candidate’s residual evaluates the complete forward export: the candidate supplies its own frozen post-Tone reference energy, then Stage 3 applies Adaptance → H–K repair → common positive Scale, followed by RGB cube containment. The search never calls a separate guard inverse, never builds a guard lookup table and never reapplies H–K repair at export.

This is deliberate. The post-tone reference energy is not known before the input is known, so a fixed-reference guard inverse has no meaning until a candidate proposes one. Inverting per component would require guessing the reference, and a wrong guess produces a candidate that fails validation anyway.

The cube projection is a separate matter: it is many-to-one and is not inverted at all. Multiple appearance requests can export to the same RGB, and the inverse returns whichever preimage the search found and ranked first. The optional hk_guard.inverse helper in the shared kernels is a standalone fixed-reference mathematical probe with a bounded scalar bisection; it is not part of this path.

20.8 Limits

The search is deterministic for a given input and model, and its result does not depend on batch shape. It is not a proof of anything. Specifically:

  • A root status means one preimage was found and verified at that residual; it does not mean the preimage is the one a user intended, nor that no closer one exists.
  • Folds in Stage 3, the signed extension, and the many-to-one cube projection can all produce several valid preimages. The ranking policy chooses among them; it does not resolve the ambiguity.
  • No global convergence is claimed. The seed set is a fixed engineering choice, and a preimage reachable only from a seed outside it will be reported as approximate or missed.
  • The 128-iteration cap and the damping bounds are safety limits; a candidate that terminates on either is reported with its actual residual rather than promoted to a root.

Any accuracy statement about this inverse is therefore a statement about a specific forward profile, a specific seed set and a measured residual distribution — not about the grade as a mathematical object.
